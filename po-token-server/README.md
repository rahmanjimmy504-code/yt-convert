# PO token server (yt-convert sidecar)

A tiny, authenticated HTTP service that mints YouTube **proof-of-origin (PO)
tokens** for the yt-convert main app.

## Why this exists

YouTube's player endpoint increasingly requires a PO token (an attestation
generated by its BotGuard/DroidGuard VM) to return playable streams for
music-label and otherwise-throttled videos. The main yt-convert app has a
hard rule of **never emulating BotGuard itself** — that logic is fragile,
privacy-sensitive, and would bloat the public deployment.

This sidecar performs the attestation (via the
[`youtube-po-token-generator`](https://www.npmjs.com/package/youtube-po-token-generator)
library, which runs YouTube's VM in `jsdom` — **no system browser needed**)
and serves the resulting `{ visitorData, poToken }` pair over a simple
authenticated API. The main app calls it *only* when you configure
`PO_TOKEN_SERVER_URL` + `PO_TOKEN_SERVER_AUTH`.

## Endpoints

| Method | Path         | Auth   | Description                                            |
| ------ | ------------ | ------ | ------------------------------------------------------ |
| GET    | `/healthz`   | none   | Liveness probe — `{ ok: true, cached }`                |
| GET    | `/api/token` | Bearer | Returns `{ visitorData, poToken }` (cached ~30 min)    |

The `/api/token` contract deliberately accepts the field names the main app
expects. It is also compatible with the shapes used by the
`lighttube-org/pot-generator` and `iv-org` generators, so you can point the
main app at a different generator if you prefer.

## Run with Docker (recommended)

```bash
cd po-token-server
cp .env.example .env
# Edit .env and set AUTH_TOKEN to a long random value:
#   openssl rand -hex 32
docker compose up -d --build
curl -H "Authorization: Bearer $AUTH_TOKEN" http://localhost:4416/api/token
```

Expose port `4416` to the public yt-convert deployment through a reverse
proxy, Cloudflare Tunnel, `ngrok`, `cloudflared`, or a security group. Use
HTTPS in front of it — the bearer token must not cross the internet in plain
text.

## Run locally without Docker

Requires Node.js 20+.

```bash
cd po-token-server
npm install
AUTH_TOKEN=$(openssl rand -hex 32) npm start
```

## Configure the main app

In the yt-convert deployment (e.g. Vercel project env vars):

```
PO_TOKEN_SERVER_URL=https://your-public-token-host
PO_TOKEN_SERVER_AUTH=<the same AUTH_TOKEN the sidecar uses>
```

Both must be set; without either, the main app simply does not request a
token and falls back to its existing Innertube → Invidious → Piped chain.

## Configuration

| Variable       | Default                | Purpose                                            |
| -------------- | ---------------------- | -------------------------------------------------- |
| `PORT`         | `4416`                 | Listen port                                        |
| `HOST`         | `0.0.0.0`              | Bind address                                       |
| `AUTH_TOKEN`   | **(required)**         | Bearer token the main app must present             |
| `TOKEN_TTL_MS` | `1800000` (30 minutes) | How long a minted token is reused before refresh   |

## Privacy & security notes

- The sidecar never sees end-user cookies or download URLs; it only mints a
  token from YouTube and returns it.
- Tokens are cached **in memory** of the sidecar process; they are never
  logged or persisted.
- The bearer token is the only access control — expose the service over HTTPS
  and keep it private. CORS is not enabled (it's a server-to-server call).
- A PO token makes YouTube sessions more traceable because it is tied to a
  visitor identifier. That is inherent to how PO tokens work; run the sidecar
  on infrastructure you control.

## Troubleshooting

- **`/api/token` returns 502** — attestation failed. Check the sidecar logs.
  YouTube occasionally changes its VM; update the
  `youtube-po-token-generator` dependency (`npm install youtube-po-token-generator@latest`
  and rebuild the image).
- **Main app does not use the token** — confirm both `PO_TOKEN_SERVER_URL`
  and `PO_TOKEN_SERVER_AUTH` are set, and that the deployment can reach the
  sidecar host. The main app logs nothing about tokens for privacy reasons,
  but a misconfigured URL simply returns no token and extraction continues
  without it.
